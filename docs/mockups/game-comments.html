Game Page Comments

Three ways to let players talk about a game on its page. They differ in what a comment is attached to: a playthrough the player already logged, a free-standing thread, or both in one panel. Every example below is drawn for Hollow Knight with invented usernames.

Placement
Full-width panel after Details and before Release dates — the page is already long, so it sits below the facts.
Already stored
Playthrough notes with status, platform, hours and date; 1–10 user ratings; RichEditor and RichText.
Constraint
Game pages are ISR for an hour and must carry content in the server HTML.
Reality check
~376k games. Almost every page opens with zero comments, so the empty state is the common one.
A

Reviews from playthroughs

A comment is a playthrough note the player chose to publish. Nothing new to write — the note already exists, and it arrives with context no free comment has: how far the player got, on which platform, and in how many hours.

Works because

  • No new editor or form — "Write a review" opens the playthrough modal the player already knows.
  • Every review carries status, hours and rating, so a "Dropped · 12 h · 5/10" reads differently from "Mastered · 46 h".
  • Cheapest to build: one flag on playthroughs, one read endpoint, one helpful counter.

Costs

  • Existing notes were written as private — publishing must be opt-in per playthrough, never a migration.
  • No replies. A question like "Switch or PC?" has nowhere to go.
  • One review per playthrough, so a replay shows the same player twice unless grouped.
B

Discussion thread

A comment is its own object with one level of replies. Anyone signed in can ask or answer. The player's status on the game is still shown next to their name, so an answer from someone who finished it is recognisable at a glance.

  • Short questions add little to the HTML a search engine sees, compared with reviews.
C

Reviews and discussion in one panel

One panel, two tabs. Reviews (variant A) open by default and lead with what players who finished the game thought; Discussion (variant B) sits one click away. Each tab has its own way to contribute.

How it would be built

Written for C, since it contains A and B. Shipping A alone is the first two rows of each block.

Data

// packages/schemas/src/playthroughs.schema.ts
isPublic: z.boolean().optional()
isSpoiler: z.boolean().optional()
helpfulCount: z.number().optional()

// packages/schemas/src/comments.schema.ts
CommentSchema = z.object({
  _id, gameId, userId,
  parentId: z.string().optional(),
  playthroughId: z.string().optional(),
  body: z.string().max(4000),
  isSpoiler: z.boolean(),
  likesCount: z.number(),
  repliesCount: z.number(),
  status: z.enum(["visible", "hidden", "deleted"]),
  createdAt, updatedAt,
})

Indexes: { gameId, isPublic, helpfulCount } on playthroughs, { gameId, parentId, status, createdAt } and { gameId, likesCount } on comments, unique { commentId, userId } on likes.

API

GET    /games/:gameId/reviews?status=&sort=helpful|new&cursor=
PUT    /playthroughs/:id/helpful   · DELETE to undo
GET    /games/:gameId/comments?sort=top|new&cursor=
GET    /comments/:id/replies?cursor=
POST   /comments
PATCH  /comments/:id   · author only
DELETE /comments/:id   · soft delete, keeps replies
PUT    /comments/:id/like
POST   /comments/:id/report
PATCH  /admin/comments/:id   · hide / restore

Bodies go through sanitizeRichText like playthrough notes. Cursor pagination, not page numbers, so a new comment does not shift the next page.

Server HTML and caching

  • app/games/[slug]/page.tsx fetches the first page of reviews next to getGame, wrapped in cache(), and passes it as initialData.
  • The page stays ISR for an hour. The client query refetches on mount, so an author sees their review immediately while the HTML catches up.
  • Do not call revalidateGamePage on every comment — a busy thread would turn the page into a cold render on each post.
  • Reviews with a rating can go into the game's JSON-LD as review entries; discussion stays out of it.

Web

  • entities/comment/api — keys, queries, mutations, following the playthrough entity; likes and helpful update optimistically.
  • features/game/GameComments — the panel; bodies render only through RichText, the composer is RichEditor.
  • Status next to a name comes from the author's playthrough for this game, returned by the API with the comment.
  • Spoilers are blurred with CSS while the text stays in the HTML, so nothing is gated on client state.

Recommendation

Build C in two steps, starting with the Reviews tab

Step one is variant A inside C's panel: publish toggle and spoiler toggle in the playthrough modal, a read endpoint, a helpful counter and the empty state. It needs no moderation queue and gives game pages real text in the server HTML. Add the Discussion tab once there are enough published reviews to show that players want to talk on game pages at all.

Colours, spacing and radii are the project's own tokens: the :root block above is generated from apps/web/src/lib/app/styles/vars by bun --filter web sync:tokens. The typeface is substituted — Hanken Grotesk stands in for ApercuPro, whose licensed file cannot be served from a third-party host. Usernames and texts are invented examples. Icons are drawn inline for the mockup; on the site each one becomes an Svg* component in shared/ui/svg.
