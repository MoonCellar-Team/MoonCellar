News and articles

A new section where admins publish two kinds of posts: site news (plain text, like a changelog entry with a picture) and game articles, which are written about one game from the catalogue and show that game next to the text, with its cover, score and the same tracking controls as a game card. What is being decided is where that game sits while someone reads, and how the feed looks. All three options use the same data and the same editor; they differ only in layout.

Decision
Variant A. Beside the feed: an archive by year and month and a game filter, not a "Games in the news" panel, since every game article already names its game. B and C stay below for reference.
Routes
/news for the feed, /news/[slug] for a post. Both rendered on the server: posts are meant to be shared and found in search. The header gets a News link. The archive and the game filter live in the query string: /news?year=2026&month=9, /news?game=signalis.
Two kinds of post
Site news: title, summary, optional image, text. Game article: the same plus one linked game. Without its own image it takes the game's artwork.
Who writes
Admins only, from /admin/news. The text is the shared RichEditor and goes through the API's sanitizeRichText, like reviews.
Link previews
The post's image as og:image; a game article without one uses the game's cover, as game pages do; otherwise og-default.png.

Sidecar

Chosen

The text gets the wide column and the game gets a fixed column on the right that stays put while you scroll: cover, score, how MoonCellar players are getting on with it, and the four tracking controls. Site news uses the same frame and puts the latest posts in that column. The feed keeps the article's two columns: the list, and beside it an archive by year and month with post counts, plus a search for articles about one game, the way blogs do it. Below 900px the archive becomes one dropdown above the list. Trades text width for keeping the game in view the whole time.

Gains

  • The game never leaves the screen on desktop, which is exactly the brief.
  • Room for tracker data no other site has: how many players finished it, dropped it, are playing it.
  • One page skeleton for both kinds of post; only the right column changes.

Costs

  • Text and panel share the row: between 900 and 1080px the text gets narrower than in B and C.
  • On a phone the panel is seen once, under the title, and scrolls away.
  • Looks like a classic blog; the least MoonCellar-specific of the three.
B

Game frame

A game article opens the way a game page does: the game's artwork across the top, the cover overlapping it, and the background of the whole page taken from the game. The title of the article sits where the game's name would, with the game's name above it as a link and the tracking controls beside it. The text below runs in one centred column. The feed is a magazine: a lead story, then cards that carry the same cover-over-artwork mark. Trades keeping the game in view for a page that clearly belongs to that game.

Gains

  • Reads as part of MoonCellar: the same hero, cover offset and background as a game page.
  • The text keeps a full centred column, the most comfortable to read of the three.
  • The feed has a clear lead story, so a big article gets the attention it deserves.

Costs

  • Once the hero scrolls away, the game is gone until the end of the article.
  • Every game article needs good artwork; a game without any falls back to a plain banner.
  • The magazine grid needs a lead story; a week of short site news makes it look thin.
C

Timeline and dock

The feed is a timeline by month, drawn with the release calendar's day numbers and axis, and every game article is marked on it by the game's cover. Inside an article, the game sits in a slim bar docked above the text, and it follows the reader down the page: under the header on desktop, at the bottom of the screen on a phone, where the thumb is. The editor also gets a "Game" block, so an article can show other games it mentions as cards inside the text. Trades build effort for the only layout that handles several games per post.

Gains

  • The game is one tap away on every screen size, including phones.
  • A post can feature several games: one pinned, the rest as cards in the text. Roundups ("five games for a long weekend") become possible.
  • The timeline shows how active the section is at a glance and reuses the release calendar's look.

Costs

  • The most work: a new RichEditor node, its sanitizer rule on the API, and a game lookup when the post renders.
  • The dock is thin, so there is no room for the "how players track it" numbers from A.
  • A timeline wastes width on a month with one post.

Writing a post

The same for all three variants. The kind of post is a switch at the top; "Game article" adds the game picker. The dashed "Game" tool in the editor exists only in variant C.

Any of them needs

A size="article" prop on RichText that calls the existing richText(17px, 28px) mixin with a wider block gap and full-width images: reviews are set at 14px, which is too small for a 6-minute read. A new SvgNews icon for the header link. An articles module on the API with type: "news" | "game" and an optional gameId.

Colours, spacing and radii are the project's own tokens: the :root block above is generated from apps/web/src/lib/app/styles/vars by bun --filter web sync:tokens. The typeface is substituted — Hanken Grotesk stands in for ApercuPro, whose licensed file cannot be served from a third-party host. Covers and artwork are colour placeholders; the players, counts and the admin account nightshift are invented.
