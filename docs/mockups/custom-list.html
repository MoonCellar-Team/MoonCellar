Custom Lists

Next to the seven fixed categories, a player can make lists of their own — named, described, in their own order — and anyone can open one by link. This page draws two ways to lay out a list and the pieces both of them share: the entry in the profile navigation, the dialog that creates and edits a list, the search that adds a game, and the states a list goes through. Adding a game from a game card or a game page is drawn in its own mockup. Every example belongs to the invented profile moth_scholar.

Placement
A Lists panel in the profile's navigation column; a ?list=lists tab with every list; each list at /user/<name>/lists/<slug>.
Data assumed
Its own collection: userId, name, slug, description (≤ 300), isPrivate, ordered games[] of { gameId, addedAt }, updatedAt.
Must have
Create a list from the profile; search for a game on the list page and add it; remove games; public and private lists.
Replaces
The owner-only Edit row under the categories, which opens the unfinished CustomFolder modal (“Create new folder”).
Open limits
Up to 50 lists per player and 500 games per list are placeholders, to be decided.
A

Shelf grid

The list looks like every other list on the profile: the same GamesCards grid of covers, 30 per page like the categories, sorted from the navigation column. Search sits in the header and drops its results over the grid through the portal. Manage switches the grid into edit mode — a remove button and the position on each card, and cards can be dragged.

Best for visitors, who scan covers. Weak for curating: dragging a card across a wrapping grid is imprecise, worst on a phone, and the order is only readable from the small position numbers. Every card is a link in the server HTML, so a public list is indexable as it is.

B

Ranked rows

The list reads as a ranking: a numbered row per game with its year and platforms, and — for whoever is looking — their own status and rating of that game, so a visitor sees at once what they have already played. The owner gets a drag handle and a remove button on every row. Add games opens a search panel pinned above the first row; results are added at the top or at the end, and the panel stays open for the next one.

Best for curating, and the only layout where the order itself is legible. Costs a new row component and a drag-and-drop dependency, shows far fewer covers per screen, and differs from every other list on the profile. Rows are plain links, so it is as crawlable as A.

How it would be built

Everything below is shared by both variants; only the list body differs.

API

GET    /users/:name/lists        private ones for the owner only
GET    /lists/:slug?user=:name   404 if private and not the owner
POST   /lists                    { name, description?, isPrivate }
PATCH  /lists/:id                { name?, description?, isPrivate? }
DELETE /lists/:id
POST   /lists/:id/games          { gameId, position: "start" | "end" }
DELETE /lists/:id/games/:gameId
PATCH  /lists/:id/order          { gameIds: string[] }

Every write checks the owner. order takes the full id list and is rejected unless it holds exactly the stored games, so two tabs cannot silently drop one. The game read pages 30 at a time in the stored order and joins the game fields the cards need.

Data

  • Zod schemas in packages/schemas (custom-lists.schema.ts): the list, create and update requests (name trimmed, 3–60; description ≤ 300), add and reorder requests.
  • New collection with { userId, slug } unique and { "games.gameId": 1 }, which answers “which of my lists hold this game” for the game-card popover.
  • Ids declared as Schema.Types.ObjectId paths, not bare ref, or string ids match nothing.
  • Slug from the name; a clash inside one profile gets -2. Names are unique per player, case-insensitively.
  • A game appears in a list at most once.

Web

  • Route app/user/[name]/lists/[slug], rendered on the server with the first page of games; notFound() only from the page component, never from generateMetadata.
  • UserNavigation gains the Lists panel; the categories' Edit row and CustomFolderModal are removed.
  • UserLists for ?list=lists; ListModal for create and edit, fields wired through Controller; ListSearch built on Input with results through the #dropdown-connector portal, reusing the catalogue's name search.
  • Add and remove are optimistic React Query mutations that also refresh the game-card popover's data.

Activity, icons, tokens

  • Lists never write to the activity feed: adding, removing and reordering games leave no log, or the feed would fill with filing instead of playing.
  • New Svg* components: SvgLock, SvgGrip (B only), SvgCheck. SvgList, SvgLink, SvgPlus, SvgSearch, SvgPen, SvgClose exist.
  • Tokens to promote: --mock-search-width, --mock-row-cover-width, --mock-rank-width, --mock-handle-size, --mock-row-action-size.

Open questions

  • Limits: 50 lists per player and 500 games per list are placeholders.
  • Renaming changes the slug. Keep old slugs as redirects, or let shared links break?
  • Can a visitor copy someone else's list into their own?
  • Are the five favourite games a list of their own, or separate from lists? They are drawn in the profile mockup.

Not in this round

  • A note per game inside a list.
  • Lists with several authors.
  • A public directory of everyone's lists.

Recommendation

Variant A, with B's rows as its Manage mode

Visitors read a list the way they read the rest of the profile, so the page stays the cover grid they already know, and it ships mostly from existing components. Ordering is the one job the grid does badly, so Manage swaps the grid for B's compact rows — handles, remove, and the pinned search with top or end — and Done swaps it back. If lists turn out to be mostly rankings, B's rows can become the default view later without changing the API.

Colours, spacing and radii are the project's own tokens: the :root block above is generated from apps/web/src/lib/app/styles/vars by bun --filter web sync:tokens. The typeface is substituted — Hanken Grotesk stands in for ApercuPro, whose licensed file cannot be served from a third-party host. Covers are coloured placeholders, and the profile, its lists and the dates are invented. Icons are drawn inline here; on the site each one is an Svg* component in shared/ui/svg.
