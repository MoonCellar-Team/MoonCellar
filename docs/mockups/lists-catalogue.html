Lists Catalogue

A page for every public list on the site, built the way /games is: filters in the left drawer, results in one panel, pagination pinned to the bottom. The search modal's Lists tab hands its query over to it, the way the Games tab hands over to the catalogue. What is being decided is how a list reads in a grid of hundreds — as a cover mosaic or as a row with a strip of covers. The players and lists are invented; queries match the Search Modal mockup.

Route
/lists, rendered on the server from the query string like /games. A header link sits next to Games.
Entry points
"More lists" and "Advanced" in the search modal's Lists tab open /lists?search=…. The header link opens it unfiltered.
What is listed
Public lists with at least one game. A private list never appears, not even to its owner — they have it on their profile.
Filters
Name and description, author, games the list contains (any or all), size, last update; sort by update, creation, size or name.

From the search modal to the page

The Lists tab changes in one place: its bottom button no longer loads more lists into the modal. It becomes "More lists", and "Advanced" appears in the field — both go to the catalogue with the query already applied, exactly as "More games" and "Advanced" do on the Games tab. The Users tab keeps "Show more" inside the modal; there is no user catalogue.

Mosaic grid

Each list is a cover-shaped tile made of its first four covers, with the name, the author and the size under it — the same proportions as a game card, so the page feels like a sibling of /games. Drawn as a visitor arrives from the modal: the query is applied, the drawer is open, and the applied filters repeat above the grid as removable pills.

  • Reads like /games: tiles in cover proportions, the drawer, the pinned pagination.
  • Most lists per screen — three or four columns of 24 per page.
  • A list is recognised by its covers before its name is read.

Costs

  • The description gets two clamped lines at most, and only when it explains the match.
  • Four covers say little about a list of 200 games.

Rows with a cover strip

Each list is a row: a fanned strip of its first five covers, the name large, the author, two lines of description, and the size on the right. Lists are chosen by what they are about, and this layout gives the words room. Drawn unfiltered with the drawer closed.

Fields

  • Sort by — Recently updated (default), Newest, Most games, Name; the arrow toggle flips the order.
  • List name — matches the name and the description; name matches rank first, as in the modal. Enter applies, as on /games.
  • Author — a user name, prefix match.
  • Contains games — the catalogue's game search inside the dropdown. Any: holds at least one of them. All: holds every one. This is also what lets a game page link to "public lists with this game" later.
  • Last updated — Any time, Past week, Past month, Past year.
  • Size — "From N games", the same single-thumb range as rating on /games.

Not in this round

  • Saved filters (the Saved tab of the games drawer).
  • Genres or platforms of the games inside a list — it needs aggregates per list, kept up to date on every change.

How it would be built

Most of this is the lists search endpoint from the modal, extended with filters.

API

GET /lists?search=&author=&games=&gamesMode=
          &minGames=&updated=&sortBy=&sortOrder=
          &page=&take=24
  • One endpoint serves the catalogue and the modal's Lists tab (take=6); the separate /lists/search from the Search Modal mockup is no longer needed.
  • Always isPrivate: false and at least one game; the response carries the first four or five game covers and the author's name and avatar only.
  • A stored gamesCount kept by the add and remove writes, so size filtering and sorting do not count arrays per request.
  • Indexes: a partial index on isPrivate: false with updatedAt, gamesCount; the existing games.gameId index answers "contains". autoIndex builds them on production at first load.

Web

  • app/lists/page.tsx mirrors app/games/page.tsx: parses the query, fetches the first page on the server, passes initialData, adds breadcrumb and ItemList JSON-LD.
  • ListsPage mirrors GamesPage: ExpandMenu with ListsFilters, fixed Pagination, page changes through pushState, not router.push.
  • ListsFilters is a new component built from the same pieces as Filters; the games drawer is not made generic.
  • The tile (A) becomes one ListCard, shared by the catalogue, the profile's Lists tab and the search modal.
  • A grid of 24 divides into 4, 3, 2 and 1 columns, so no page ends in a ragged row.
  • Header: a "Lists" link with SvgListBullet between Games and Gauntlet.

Recommendation

Variant A

The catalogue is for browsing many lists quickly, and A shows twice as many per screen with the tile that the profile and the search modal already use — one component instead of two. B's strength, the description, is what the list page itself is for, one click away.

Colours, spacing and radii are the project's own tokens: the :root block above is generated from apps/web/src/lib/app/styles/vars by bun --filter web sync:tokens. Covers and avatars are gradient placeholders, the players and lists are invented, and the Gauntlet icon is a stand-in. The typeface is substituted — Hanken Grotesk stands in for ApercuPro, whose licensed file cannot be served from a third-party host.
