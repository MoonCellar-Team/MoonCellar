Profile Reviews

Three ways to show everything one player has written, on their own profile. The reviews already exist — they are the playthrough notes published to game pages — so what is being decided here is how a hundred of them are read, filtered and sorted in a single column. Every example is drawn for the invented profile moth_scholar.

Placement
A list of the profile, next to All / Completed / Wishlist — ?list=reviews, inside the same content Box.
Already stored
Playthrough note, status, platform, hours, finish date, 1–10 rating, helpful count, spoiler and publish flags.
Must have
Sorting, newest first by default; filters by game, by status and by rating.
Reality check
Most profiles hold between zero and thirty reviews; a heavy user has a few hundred, some of them a screen long.
A

One column, full texts

The game page's review list, pointed at a player instead of a game: the cover replaces the avatar, and every filter sits in one toolbar above the feed. Reviews are read where they are listed — nothing opens, nothing navigates.

Works because

  • One component for both places — the game page's ReviewItem with a cover where the avatar was.
  • A long review is read in place; nothing is hidden behind a click.
  • The toolbar holds all three filters and the sort at once, so the current selection is always visible.

Costs

  • Three reviews fill a screen. Finding one written a year ago means paging through or filtering by game.
  • The toolbar is three rows tall on a phone before a single review is shown.
B

Cards on a grid

Every review is a card: cover, game, status, rating, and the first five lines of the note, with the cards of a row sharing one height. The grid follows the profile's own game lists, so the Reviews list looks like a list of games the player wrote about. Full text opens in the reading modal ExpandableBlock already uses.

Reviews are opt-in, so the list is empty on nearly every profile until the player publishes a note. It is the same block in all three variants.

How it would be built

The read endpoint is the same for all three; only the panel differs.

API

GET /user/:userId/reviews
      ?gameId=&status=&ratingMin=&ratingMax=
      &sort=date|rating|helpful&order=asc|desc
      &page=&take=

One aggregation over playthroughs: the author's rating of each game is joined in, so rating can be filtered and sorted on. The answer carries summary (counts per status, average rating) for the chips and games for the game filter, both counted over the unfiltered set.

What a visitor sees

  • Every note the player wrote. The publish flag decides whether a note also appears on the game's page, not whether it appears here; on their own profile the author sees which ones are Not published.
  • Wishlist entries never appear — a note on a game nobody played is not a review.
  • Spoilers stay blurred behind Spoiler, exactly as on the game page.

Web

  • ?list=reviews next to the profile's other lists, with its own entry in UserNavigation and the count beside it.
  • Filter state lives in the URL, so a filtered list can be linked and Back works.
  • Texts render through RichText only; the game filter is a Dropdown with isThroughPortal.

Sorting

  • Newest is the default and means the review's last edit, not the finish date — an old playthrough rewritten today belongs at the top.
  • Rating puts unrated reviews last whichever direction is chosen.
  • Helpful is the game page's counter, so the profile agrees with it.

Recommendation

Variant A, with B's card grid kept in reserve

A is the review list the site already has, and a profile is read the way a game page is read — top to bottom, whole texts. It ships as one component reused from the game page and needs no new layout rules. B becomes worth building once profiles routinely hold more than fifty reviews; C is the answer to a problem no profile has yet.

Colours, spacing and radii are the project's own tokens: the :root block above is generated from apps/web/src/lib/app/styles/vars by bun --filter web sync:tokens. The typeface is substituted — Hanken Grotesk stands in for ApercuPro, whose licensed file cannot be served from a third-party host. Covers are coloured placeholders, and the profile, its reviews and the dates are invented. Icons are drawn inline here; on the site each one is an Svg* component in shared/ui/svg.
