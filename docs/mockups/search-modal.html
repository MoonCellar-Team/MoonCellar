Search Modal

The header's Search opens a modal that finds games only. It now has to find people and their public lists too, from the same field. What is being decided is how the three kinds of result share one modal: behind category tabs, or mixed into an overview first. Every example searches for hollow; the players and lists are invented, and the lists are the ones drawn in the Custom Lists mockup.

Placement
SearchModal, opened from the header with modal.open(…, { id: "search-games" }). No route of its own, nothing server-rendered.
Today
At least 2 characters, 500 ms debounce, 30 games in a 4-column GamesCards, "More games" and "Advanced" lead to /games?search=.
New categories
Users by user name. Lists by name and description, public lists only — a private list never appears, not even to its owner here.
Reality check
User names are 3–15 characters of [a-zA-Z0-9_]. There is no user search yet: GET /user/search matches one exact name or e-mail.
A

Category tabs

A tab row sits under the field: Games, Users, Lists, each with the number of matches. Games is selected by default, so the search people use today works exactly as before. Switching a tab keeps the text and shows that category's results. Every tab fetches its own count, so the counts are also how you learn another category has matches.

More lists

"More lists" and "Advanced" open the lists catalogue with the query applied, /lists?search=hollow, and close the modal — as "More games" and "Advanced" do on the Games tab. The catalogue is drawn in the Lists Catalogue mockup.

Works for

  • Game search, the reason the modal exists, keeps its screen and its "Advanced" button.
  • Only one category renders at a time, so each keeps a layout suited to it: covers, rows, cards.
  • The counts answer "is there anything elsewhere" without switching.

Costs

  • Three requests per query for the counts, even when only Games is open.
  • Someone looking for a person has to notice and press the tab; a player named "hollow…" is not visible from the Games tab.
B

Everything first, then tabs

A fourth tab, All, opens by default and shows the top of every category in one scroll — a row of games, a few players, a few lists — each with a link to its own tab. It suits a search where people type a name without saying what it is. It also makes every search slower and noisier for the common case of looking for one game.

What a result shows

Only what an anonymous visitor could already see on the profile or the list page. The matched part of the name is highlighted.

User row

  • Avatar, user name, last seen — as on the profile.
  • Games and followers counts, so two similar names can be told apart.
  • The first favourites as tiny covers, when the player has set any; hidden on phones.
  • Follow / Following for a signed-in viewer; nothing for guests and on your own row. "Follows you" when it applies.
  • The row opens /user/[name] and closes the modal, as a game card does today.
  • Ten rows per page; with more matches a "Show 10 more users" button appends the next page inside the modal.

List card

  • The same four-cover mosaic as the profile's Lists tab.
  • Name, author with a small avatar, game count, last update.
  • When the match is only in the description, one clamped line of it replaces the date, so it is clear why the list came up.
  • Empty public lists are not returned — they are dead ends.
  • The card opens /user/[name]/lists/[slug].

How it would be built

The same data work serves both variants; B adds a preview request on top.

API

GET /games?search=&take=        exists, returns total
GET /users/search?q=&page=&take=  new
GET /lists?search=&take=6           new, public lists only
GET /search/counts?q=              new: { games, users, lists }
  • GET /user/search must not be reused: it matches an exact e-mail too, so a public search box would confirm whether an address has an account.
  • Users: names that start with the query first, then names that contain it; case-insensitive; the query is escaped before it becomes a regex. Only public fields are returned — never e-mail, settings or the follower arrays.
  • Lists: isPrivate: false and at least one game; name matches rank above description matches.
  • Both new endpoints are open to guests, so they get a rate limit.

Indexes

  • userName has a case-sensitive unique index, which a case-insensitive regex cannot use. Add a lower-cased userNameNormalized kept by a save hook — the same approach as nameNormalized on games — and index it.
  • Lists get a normalized name as well, in a partial index on isPrivate: false; a description match can scan, since it only runs after name matches are exhausted.
  • Remember that autoIndex builds new indexes on production the first time a local process loads the schema.

Web

  • SearchModal keeps its field, debounce and 2-character minimum; a tab row built on the shared Tabs goes under it.
  • The selected tab lives in a small persisted store, so the modal reopens where it was left; the modal id changes from search-games to search.
  • New hooks useUsersSearchQuery, useListsQuery (shared with the catalogue), useSearchCountsQuery; full results are enabled only for the open tab.
  • "Advanced" and the bottom button lead to a catalogue on the Games tab (/games) and the Lists tab (/lists). Users have no catalogue.
  • Users load in pages of 10 through useInfiniteQuery, and "Show 10 more users" appends the next page inside the modal until the total is reached.
  • Rows and cards close the modal on navigation, as the existing asPath effect already does.

Icons and tokens

  • No new icons: SvgGames, SvgProfile, SvgListBullet and SvgSearch exist.
  • To promote into vars/_components.scss: --mock-modal-width (today the 900px lives in the module), --mock-result-avatar, --mock-list-mosaic, --mock-tab-height.
  • The match highlight is a new style for mark, accent at 38% — none exists on the site yet.

Recommendation

Variant A

Almost every search is for a game, and A leaves that search exactly as fast and as full as it is today. The counts on the tabs do the one job B's overview was for — telling you that players or lists matched — without pushing the game grid down. The "nothing here, found elsewhere" state covers the moment someone searches on the wrong tab.

Colours, spacing and radii are the project's own tokens: the :root block above is generated from apps/web/src/lib/app/styles/vars by bun --filter web sync:tokens. Covers and avatars are gradient placeholders, and the players and lists are invented. The typeface is substituted — Hanken Grotesk stands in for ApercuPro, whose licensed file cannot be served from a third-party host.
